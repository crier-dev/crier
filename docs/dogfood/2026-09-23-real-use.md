# Crier dogfood — real-use run, 2026-09-23

Target: `/home/kara/crier` @ `3aac658` (`v0.1.0-rc2-19-g3aac658`), a scratch
server per arm, in-memory backend unless stated, agent signing ON by default,
LLM guard OFF except where a guard arm says otherwise. Scratch dir
`/tmp/dogfood-crier-0923/`. Nothing in the repo was modified by the run itself;
the artifacts below were added afterwards.

This run's **angle** (chosen to avoid repeating the last entries in
`.coding-hermes/dogfood-log.md`): the **federation hold/retry contract** driven
end-to-end *including the recovery forward* (`specs/WEBHOOK-DELIVERY.md` §8.1 —
the 2026-09-14 run covered hold + crash recovery but never watched a held
delivery land on a link that came back), the **mesh wire protocol** driven from
a raw client, the **multi-endpoint workflow**, and **performance of the
headline operations**. Prior runs covered the inbox/webhook/guard/Postgres/MCP
surface; where this run re-treads 09-14 ground it is marked as confirmation, not
as a first.

## Promise under test

A fresh user can install crier on a clean machine, and two autonomous agents on
two separate relays exchange real work across a federated link — a delivery to
an agent on the other bus reaches it, its reply returns to the original sender,
the message survives the link going down and is recovered when the link comes
back, and an agent pair can also talk peer-to-peer over the mesh with
request/response correlation.

## Verdict

**PROMISING-BUT-ROUGH → SHIPPABLE on behaviour, ROUGH on install docs.** Every
promised primitive completed live, including the one arm I had not seen
exercised: a held delivery watched landing on a link that came back (`#3`
below), plus the mesh's malformed-frame refusals and body passthrough. Outcomes
#1/#2/#4/#5 confirm what the 2026-09-14 run found. The federation contract is
the strongest thing in this project — it behaves exactly as specified, down to
the correlation fields. The roughness is in the **install path for a fresh
non-root user** and in one **silent empty-content trap** in the webhook schema
template.

Time-to-first-success: **~90s on a fresh Debian 13 box** (9s Go install, 35s
build, then a completed signed round-trip), but **only after a detour the docs
do not cover** (`xxd` — see DF-CRIER-280). On a warm dev host: 17ms to a
healthy server, 180ms for the whole demo round-trip.

**Two frictions, both in the docs, not the code** (DF-CRIER-280): the box has
no `xxd`, and `examples/demo.sh` refuses to run without it (`ERROR: xxd required
(hex encoding)`, exit 1). The README gives a careful non-root installation path

**does not work on Debian 13**: `vim-common` contains no `xxd`. The package is
its own: `apt-get download xxd` → `dpkg -x` → `~/bin/xxd` works without root.
A real user burns 10-15 minutes on this.

### Federation hold / retry — the documented contract, all five outcomes

Two real relays, hold budget set to 20s so the terminal case is reachable:

| # | Scenario | Documented | Measured |
|---|---|---|---|
| 1 | link down, **no sender** on the body | `502 FEDERATION_FAILED`, never held | **502 in 0.7ms**, `detail` names the absent sender |
| 2 | link down, **sender** named | `202 {"status":"held"}` | **202 in 3.1ms**, durable queue file on disk (608 bytes) |
| 3 | link comes **back** | held delivery recovered and forwarded | **recovered in ~2s**, `held delivery recovered — relayed to the linked relay`, queue file reloaded to `{"items":[]}` — **first time this arm has been watched live** |
| 4 | link down, target exists nowhere | `404`, budget not waited | **502/404-class in 0.8ms** — no hold |
| 5 | held past the budget | one terminal notice in the **sender's** inbox | **arrived**, `{"kind":"error","code":"FEDERATION_FAILED",…,"attempts":4,…}` with `message_id`/`target`/`sender`/`request_id`/`attempts`/`error` all populated |

This is the part of crier I would vouch for. "An outage must never be reported
as agent not found" holds live; every correlation field the spec makes required
is actually present.

### Mesh wire protocol, driven from a raw client

Following `docs/mesh-protocol.md`'s worked example, then the paths it does not
show:

- 20 request/response round trips each way: **a→b 0.257ms mean, b→a 0.262ms
  mean** (max 0.577ms)
- `REGISTER_ACK` — **never sent** (docs say defined-but-never-sent: confirmed)
- **wrong `request_id` on a RESPONSE** → silently dropped, requester times out;
  the socket is **still usable afterwards** (documented, confirmed)
- target not connected → `ERROR CONTROLLER_OFFLINE` with `request_id` echoed
- a non-JSON frame → `ERROR INVALID_MESSAGE` **with `request_id` absent** (correct:
  nothing to correlate)
- an unknown `type` → `ERROR INVALID_MESSAGE` **with `request_id` echoed** (correct)
- a blank `target.agent_id` → `INVALID_MESSAGE … expected target.agent_id`
- a `source` that is not a `PeerRef` object → `INVALID_MESSAGE` naming the Go
  type error, `request_id` echoed
- **body type passthrough** confirmed both ways: a string body arrives as a
  string, an object body as an object

### Relay pub/sub

Subscribe-then-publish over a live WebSocket: publish accepted in **1.16ms
mean** and the frame in the subscriber in **1.288ms mean** (max 1.856ms), 20/20
frames arrived. The server KEEPALIVE arrived at **27.25s** with
`"agent_id":"crier"` on the socket — the docs' "the server's mesh identity, not
the peer's id" is exactly right.

## Performance (Step 2b)

All numbers are from this run's real operations; commands are in the
diagnostics trail. **Verdict: nothing here is slow enough for a user to
notice, so no `PERF-<n>` row is filed.**

| Operation | Cold | Warm |
|---|---|---|
| server start → first `/health` 200 | **17.1ms** | — |
| deliver (guard off) | — | **1.58ms** mean, 1.9ms p95, 2.35ms max (30 runs) |
| signed retrieve | — | **8.8ms** mean, 10.65ms p95 |
| signed ack | — | **9.52ms** mean |
| `GET /agents` at 10 vs 100 agents | — | 1.54ms → **1.97ms** p50 (no blow-up) |
| federated blocking delivery (2 relays + webhook) | 3.1ms | **8.0ms ± 0.6ms** (30 runs) |
| same, local (no federation) | — | 7.1ms ± 0.3ms |
| ghost agent, all links 404 | — | 7.5ms ± 0.6ms |

**The honest decomposition matters here.** `hyperfine` reports 8.0ms for the
federated delivery, but its own split is `User: 2.5ms System: 4.3ms` — 6.8ms of
that 8.0ms is **curl's own process startup**, not crier. The server's own
handler lines say the same thing from the other side: every endpoint logs
**20-270µs** (`/agents/{id}/inbox` 166µs, `DELETE /agents/{id}` 21µs, the 404
path 42µs). So the thing you would actually feel is on the order of **1-2ms
of server time**, and the federated hop costs ~0.9ms over a local delivery. No
profile was justified; no flamegraph was taken.

One number that is *not* crier's fault but worth knowing: with the guard ON (the
default) and **no provider key configured**, the guard skips the LLM call
immediately (`guard router: provider skipped … reason="no api key"`) and the
deliver still answers in **1.4-2.1ms**, with `guard.errored:true` and a reason
that names the missing key. A missing key therefore does not silently cost you
10s — the fail path is honest and fast. That is good behaviour, not a finding.

## Frictions (by a user following the docs)

- **DF-CRIER-279 (P2, silent empty content).** Register an agent with
  `schema_template: "openai-compatible"` and deliver a payload that has no
  `text` key: the template body is
  `{"messages":[{"content":"{{payload.text}}"}]}`, so the field renders
  **empty**, the webhook POST goes out with `content:""`, the endpoint answers
  200, and crier reports the delivery as **successful** — `reply: "echo: "`.
  Measured both ways with the same relay and the same payload shape: without a
  `text` key → sink saw `content=''`; with one → `content='dogfood hello over
  federation'`. `specs/AGENT-ECOSYSTEM.md:272` documents this as a trap **for
  that one sink**; the webhook config table
  (`docs/integration-guide.md:590`) documents the template without saying it
  hard-codes `payload.text`. A user whose payloads use any other key shape
  loses the message body with no error anywhere. **Fixed by DF-CRIER-279** (the
  remainder of this report is the state it was measured in): a placeholder the
  template context cannot fill now fails the delivery with an error naming
  `payload.text` and nothing is POSTed, instead of a successful delivery of an
  empty content field — `internal/webhook/schema.go`,
  `internal/webhook/schema_test.go`, `internal/webhook/logging_test.go`.
- **DF-CRIER-280 (P2, install docs).** The `xxd` gap described above.
- **CR-GAP-063 is still open and I have live evidence for it.** With
  `CR_AUTH_TOKEN` set, measured no-token: `/health`, `/version`,
  `/openapi.json`, `/openapi.yaml`, `/docs` → **200**; `/status`, `/agents`,
  `/fed/peers`, `/mesh/peers`, `/relay/topics` → **401**; correct Bearer → 200;
  wrong Bearer → 401. The stale prose is `docs/integration-guide.md:82`
  ("except `/health` and `/version`") which contradicts line 55 of the **same
  file** ("the five exempt paths"). The open row's claim is correct; the
  specific line to fix is 82.
- **DF-CRIER-282 (P3, contract gap).** On a **recovered** federated delivery the
  forward's reply reaches nobody and the spec does not say what the 202'd sender
  should expect. Live: the sender got `202 {"status":"held"}`, ~2s later the
  relay logged `held delivery recovered … status=200 response_bytes=109
  response="{\"id\":…,\"reply\":\"echo: …\"}"` — and that reply is then dropped.
  §8.1 defines the three outcomes for the *first* attempt and the terminal
  notice, but says nothing about the reply of a recovery. A sender that needed
  the reply has no documented way to get it.
- **DF-CRIER-281 (P2, process — the leak class is still live).** `CR-GAP-069`
  asked for two things. Ask #1 (the trap+port-freed contract for scripts) landed
  as `scripts/check-demo-cleanup.sh` + CI. **Ask #2 (a tick-start orphan sweep)
  was never implemented**: the string `orphan` appears nowhere in
  `coding-hermes-dogfood/SKILL.md`, nowhere in this lane's scheduler prompt, and
  no fleet script performs a crier-specific sweep. The new gate cannot cover the
  gap either — its scope is `git ls-files '*.sh'`, i.e. **TRACKED** scripts, so
  an ad-hoc `/tmp` dogfood script (exactly what leaked the two servers) is
  structurally invisible to it. Evidence the class is live on this host right
  now: **20 `dogfood-asce*` containers** from two scratch compose stacks
  (`/tmp/dogfood-asce`, `/tmp/dogfood-asce-2026-09-07`, both 2 weeks old, **12 still running** of 20)
 holding **14 host ports** (`14222, 15434, 16380, 17700, 18081,
  18082, 18222, 24222, 25434, 26380, 27700, 28081, 28082, 28222`), plus a
  non-dogfood listener on 18080 (`helios-server`). A tick-start sweep of that
  shape would name all of them.

## Trustworthiness

- The federation hold queue is **durable and self-cleaning**: written to disk
  (608 bytes), reloaded to `{"items":[]}` after the recovery, and the terminal
  path left the sender's inbox holding exactly the notice.
- Registry `PATCH` → capability filter → `DELETE` → `404` all behaved; `PATCH`
  advanced `last_seen`, and `/status` reported a posture that matched the flags
  the server was actually started with (`auth_enabled:false`,
  `require_agent_signature:false`, `guard_enabled:false`,
  `registry_backend:"memory"`, `federation_hold_queue:"none"`).
- `/metrics` (opt-in) and `/docs` are real: `/docs` is self-contained with
  **zero external CDN references** and enumerates 14 paths / 18 operations from
  the spec; `/metrics` emits valid Prometheus text with the documented families.
- The LLM guard's fail-open path is honest: `errored:true` and a reason string
  that names the missing env var, never a clean-looking `allow`.

## What this run could NOT exercise (stated, not silently passed)
