## Promise under test

A fresh user can clone crier on a clean machine, build it, and run a real
agent-to-agent workflow: register two signed agents, deliver messages into a
durable inbox, retrieve them under lease, ack them, keep every undelivered
message across a server restart when the Postgres backend is configured — and
an MCP client gets the same registry/inbox surface over stdio.

## What was actually run (all live, on the bunker)

### Durable-inbox contract, signed (CR_GUARD_ENABLED=false, CR_REQUIRE_AGENT_SIG=true — the default)

Two agents registered with ed25519 keys (openssl 3 `pkeyutl -rawin` sigs):

1. `POST /agents` register watcher + deliverer → 200/201, keys echoed
2. deliverer → `POST /agents/watcher/inbox` signed → 201, `transport:"inbox"`,
   `expires_at` = now+24h (ttl default)
3. watcher → `GET /agents/watcher/inbox?lease_seconds=30` signed → 200 with
   lease_id + `queue_depth`/`leased_count` accounting
4. watcher → `POST /agents/watcher/inbox/ack` with lease+ids → **204**, and
   `GET .../inbox/stats` → `{"queue_depth":0,...}` — the ack is real
5. drain of 21 messages in batches (max 100 didn't matter — batches are
   per-retrieve; two extra retrieves with fresh leases drained the rest), every
   ack 204, final stats 0/0
6. relay publish to an empty topic → **202** (fire-and-forget; documented drop
   with zero subscribers — the docs' "subscribe first" contract holds)

### Cross-agent authorization (the negative cases)

- signed `eve` reading `watcher`'s inbox → **403** `agent "eve" may only access
  its own resources (target "watcher")` — the message names both parties
- bad signature → 401; missing signature headers → 401
- signed ghost agent (never registered) → **404**
- unsigned relay publish → 401 (covered by the demo as well)

### Restart survival — the two backends, contrasted

- **memory backend:** 20 undelivered messages in the queue → `kill` → restart →
  `queue_depth: 20` … *kept*?! No — this was the **same server answering**: the
  restart had silently failed to take over the port (`bind: address already in
  use` logged to a redirected log nobody read; the pidfile from the *old*
  server was still there). The old process kept serving. Caught it because the
  stats query "after restart" returned the same `oldest_age_ms` continuum.
  **This is exactly the "server runs ≠ my new server runs" trap** — and crier's
  own failure log named it perfectly (`hint_holder`, `hint_run_elsewhere`,
  build identity). Not a crier defect; a user-side verification gap that crier
  already tools for (`make stop`, the port-holder hints).
- **restarted properly** (old server killed first): memory backend loses the 20
  (expected), registry gone (expected).
- **Postgres backend** (`docker compose up -d postgres` — worked first try on
  the rootless agent socket; port overridable via `CRIER_PG_HOST_PORT`):
  registered agents + 20 undelivered messages **survived** a real restart
  (`queue_depth: 20` after, `oldest_age_ms` reset to 0 — data came back, not
  the process), then one more delivery landed (21), and a second restart
  preserved that too. `docs/integration-guide.md` §6 recipe is accurate
  including the "Migrations apply automatically" claim (no manual step was
  needed).

### MCP stdio surface (hand-rolled JSON-RPC, exactly as the README shows)

`make build-mcp && ./bin/crier-mcp` with no env → startup log names the 4
unavailable tools (`get_messages ask_agent mesh_peers mesh_request` /
`missing_env`), `initialize` answers `serverInfo.version` = build identity,
`tools/list` = 13 tools with full schemas, `register_agent` + `list_agents`
worked against the in-process store. One wire quirk the README warns about and
I confirmed: a tool result is `result.content[0].text` containing a **JSON
string** (double-parse needed), and a rejected call is `result.isError:true`,
never a JSON-RPC `error`.

## Performance (Step 2b — measured, not felt)

Server on the bunker agent (rootless container host, loopback), curl client
co-located; 20 signed ops per operation, sequential:

| Operation | mean wall per call | server-side (log lines) |
|---|---|---|
| signed retrieve (empty inbox) | 26.2ms | ~166µs (from 09-23 run; unchanged) |
| signed deliver | 30.1ms | sub-ms |
| relay publish (202, empty topic) | 11.1ms | ~40µs |
| `/health` unsigned | 8.4ms | 2.5µs |

Decomposition (the law: no claim without it): each of those wall numbers
carries curl process startup (~4.3ms sys) + ed25519 signing via an
`openssl pkeyutl` fork (~10-18ms per call — the signing helper is a
separate process per request). The 09-23 run measured crier's *own*
handler times at **20-270µs** with hyperfine on the same class of
operations, and nothing in the wire path changed since (`git log` between
`3aac658`..`ca28523` touches docs/board/qa only). **Nothing here is slow
enough for a user to notice, so no `PERF-<n>` row is filed.** The one number
worth carrying forward for client authors: with a per-request
`openssl pkeyutl -rawin` signing helper, *client-side signing* dominates
request latency by ~40x — batch signing or a linked key would be a client-side
optimization, not a crier one.

## Frictions / findings

1. **DF-CRIER-280 reproduced (P2, still pending):** xxd-less fresh Debian 13
   stops the first documented demo; `vim-common` does NOT ship xxd on Debian 13.
   Already filed 09-23 with the exact working recipe; left open for the foreman.
2. **DF-CRIER-283 (P2, new — stale-pidfile silent takeover window).** The
   sequence "kill the old server out-of-band (or lose the kill), start a new
   one on the same port" produces a new server that **logs `server failed` and
   exits while the old process keeps serving**, and the pidfile at `.crier.pid`
   (written by the old server, still on disk) is then **stale-but-plausible**:
   every later `make stop` from the recorded pid hits the wrong world. Live
   evidence: `kill $(cat .crier.pid)` after the failed takeover read a JSON
   pidfile and bash tried to kill `{`, `"pid":`… (the JSON is a real usability
   bump too — a `kill $(cat .crier.pid)` is the first thing any user tries).
   The server already names the holder (`hint_holder`) — the gap is that
   **nothing tells the user the pidfile they are about to trust describes a
   dead process**. Suggested fix direction: on failed bind, if a pidfile
   exists, refuse-and-explain ("pidfile names pid X which is dead / which is
   still running and holding the port"), and consider writing the pidfile as
   bare pid + JSON sibling (or documenting the JSON shape in `make stop`'s
   error path).
3. **DF-CRIER-284 (P3, docs gap — GOPATH collision in the Go install route).**
   The non-root tarball install (`tar -C ~ -xzf go…tar.gz`) puts GOROOT at
   `~/go`, which is also the default GOPATH → warning `both GOPATH and GOROOT
   are the same directory`. One extra line in the README's Go-install block
   (`export GOPATH=~/gopath`) removes it. A new user hitting this wastes
   minutes on a warning that looks fatal.
