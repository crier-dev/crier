# Crier dogfood — real-use run, 2026-09-19

Target: `4cfb74c-dirty` (HEAD at run). Scratch server on :18959, Postgres
backend (`crier_dogfood_20260919`, the persistence leg), LLM message guard ON
(default), bearer auth off, agent signing ON (default). Scratch dir
`/tmp/dogfood-crier-0919/`.

## Promise under test

Two autonomous agents exchange real work over crier: one registers, receives a
durable signed-inbox task, acks it; the other publishes an event to a relay
topic read over a live WebSocket; a third receives a webhook POST with the
endpoint's reply captured; and everything survives a server restart against
Postgres.

## What was actually run (all live, single workflow)

1. `make build` (1.3s) → `./bin/crier -version` prints
   `crier v4cfb74c-dirty-4cfb74c0` (identity fix holding at HEAD).
   Server boot: `crier starting port=18959 services=relay+mesh+registry`,
   registry backend `postgres`, guard + webhook delivery enabled.
2. `/health` → 200 `application/json` (content-type fix holding).
3. Signed register of two real agents (`worker-…`, `orch-…`) with real
   ed25519 keypairs → 201 `status=online`.
4. Signed deliver (`payload` = JSON object) → 201 `transport=inbox`;
   signed retrieve → 200, one message + `lease_id`; signed ack → 204.
5. Concurrent-retriever check: a second identity retrieving the same inbox
   while the lease was held got **403** (cross-agent access control held;
   the lease-exclusion semantics are documented via `leased_count`/`queue_depth`
   on the retrieve body for same-agent double-retrieve).
6. Relay: WS `GET /relay/subscribe/fleet.reports` (subscribe-first is the
   documented behavior — a topic only exists while a subscriber is connected),
   then `POST /relay/publish` with `X-Agent-ID` → 202, frame received:
   `{"topic":"fleet.reports","event":{"kind":"report.ready",…}}`.
7. Webhook: third agent registers a webhook via **signed** PATCH to a real
   local HTTP sink; `delivery_mode:"blocking"` deliver → 200 with the sink's
   reply echoed in the response body (`{"status":"ok","agent":"hooked-sink"}`),
   sink saw the full crier envelope (`crier.version/message_id/guard…`).
   Without `delivery_mode` the same deliver is accepted 202 and queued async —
   the accept body names `transport:webhook` either way (DF-CRIER-157 fix
   holding).
8. Restart durability: `pkill bin/crier`, restart on the same `CR_DATABASE_URL`
   → 14 registered agents still listed, worker present, post-restart signed
   deliver + retrieve 200. **Durability claim verified.**
9. MCP: `make build-mcp`, `crier-mcp --version` = full identity; stdio
   initialize → `serverInfo.version` = same version segment; tools/list = 13
   tools (docs match); remote store via `CRIER_HTTP_URL`+`CRIER_AGENT_ID`:
   list_agents = 14 agents, deliver_message via MCP = 201-styled message_id,
   cross-agent `inbox_stats` correctly 403s. The bridge hard-fails with a
   clear ERROR when `CRIER_AGENT_ID` is missing in remote mode (good failure).

## Frictions hit (by a user following README + examples)

- **Webhook PATCH 401 (the one real finding):** README §"Webhook delivery"
  shows webhook registration as an unsigned one-liner PATCH; live it needs the
  ed25519 signature headers (X-Agent-ID/Ts/Sig) like every other per-agent
  endpoint. Filed as **DF-CRIER-262** (P2, docs). The repo's own
  `skills/crier-usage/SKILL.md` documents the signed PATCH correctly — the gap
  is README/openapi prose only.
- `payload` must be a JSON object — a string payload is rejected 400 with a
  clear message; error message quality was fine, no finding.
- Relay publish to a topic with no subscriber is dropped (202, not retained) —
  documented in README, and the subscribe-then-publish order worked first try.
- MCP remote mode requires `CRIER_HTTP_URL` **and** `CRIER_AGENT_ID` — both
  documented in README §MCP (a user who skips that section retries once).
  Not filed: docs cover it.
