## What was exercised, and what held

### 1. Mesh REGISTER_ACK (CR-REVIEW-002 fix) — HOLDS

Both peers (`/mesh/connect/{id}`) got exactly one `REGISTER_ACK` per REGISTER,
same socket, sub-millisecond, `request_id` equal to the REGISTER's `message_id`,
`keepalive_interval_ms=30000`, `expires_at` = now+1h, and — per spec — no
`agent_id`, no payload. The first-connect client can now tell "registered" from
"dropped" without waiting out the 30s keepalive.

### 2. Mesh REQUEST/RESPONSE RPC — HOLDS end to end

alice→bob REQUEST with `source`/`target` PeerRefs relayed verbatim (body and
trace_id intact); bob's RESPONSE correlated via `request_id == message_id`,
`status_code=200`, responder-controlled body object relayed untouched. Error
paths named the request: unknown target → `ERROR` `CONTROLLER_OFFLINE` with
`request_id` match; non-JSON garbage → `ERROR` `INVALID_MESSAGE` with a specific
message ("not a JSON envelope…"). One lesson for integrators (see finding
DF-CRIER-295): `REQUEST.target.agent_id` is REQUIRED and its absence produces
`INVALID_MESSAGE: missing target peer id (expected target.agent_id)` — the
top-level `agent_id`/`to`/`payload` shapes a naive client guesses first are all
rejected. The docs say so; the error messages are what a client actually learns
from.

### 3. Relay WS keepalive (QA-CRIER-35 fix) — HOLDS

Wildcard subscriber on `/relay/subscribe/alerts.*`: received exactly the two
matching publishes (`alerts.cpu`, `alerts.disk`), none of `notalerts.x`. Then the
socket was held IDLE for 35s (crossing the 30s server keepalive cadence — the
exact scenario that used to leak half-open subscribers) and still received a
publish to `alerts.after-idle` afterwards. No reconnect needed, no stale frames.

### 4. INBOX_NOTIFY (opt-in) — HOLDS

`/mesh/connect/bob?inbox_notify=1` + REGISTER → one `INBOX_NOTIFY` per delivery,
`inbox_message_id` matching the deliver response id, `sender=alice`, no payload.
Not sent to non-opted connections (alice's socket stayed silent).

### 5. Signed HTTP inbox round-trip — HOLDS

`POST /agents/bob/inbox` (unsigned deliver, 201) → signed retrieve with
`X-Agent-ID/X-Agent-Ts/X-Agent-Sig` over `"<METHOD>\n<path>\n<unix-ts>"` → 200
with all 6 queued messages + `lease_id` → signed ack `204` → signed stats
`queue_depth=0`. Negative cases: wrong-key retrieve → 401; timestamp 120s stale →
401 (window is ±30s). One wire-shape surprise is filed as DF-CRIER-295.

### 6. RemoteStore 404 keying (CR-GAP-072 fix) — HOLDS at the MCP surface

Via `crier-mcp` remote bridge (alice as the bridge identity): `get_agent
ghost-404` and `unregister_agent ghost-404` both answer `agent not found` — the
subject the CALLER asked about, not the proxy credential `alice`. MCP stdio:
`initialize` reports `crier-mcp 0.1.0-rc2-178-g649d9e3`, 13 tools; `mesh_request`
honestly reported `unavailable_tools` with `missing_env=[CRIER_MESH_URL]` instead
of failing mid-call. `deliver_message` through the bridge landed a real message
in bob's Postgres inbox; `register_agent` validation refused a 3-char
public_key with a specific message. Startup log names the ephemeral-key fallback
when `CRIER_AGENT_PRIVATE_KEY_FILE` is unset (we set it; the log line is a good
hint).

### 7. LLM guard — live and fail-open, both observed

First server run had no provider key: every delivery carried
`guard.decision=allow, risk_level=medium, errored=true,
reason="guard_error: all providers failed: no provider api key"` — the
documented fail-open shape, and the server log emitted one
`guard router: provider skipped` line per delivery naming the provider and the
`env:DEEPSEEK_API_KEY` reference. With a real key on the server: clean allow with
NO `guard` object in the deliver body (documented ambiguity: clean-pass omission),
and the retrieve-side entries carried no verdict either — consistent with the
docs' "the object is omitted for a clean allow".

### 8. Durability (Postgres backend) — HOLDS

Server killed and restarted mid-session: agents, public keys, and undelivered
messages all survived (retrieve after restart returned the pre-restart
deliveries). `GET /status` reports `registry_backend: "postgres"`.

## Performance (Step 2b) — measured, nothing filed

- Warm `GET /health`: 5.0ms ± 0.4 (hyperfine, 20 runs). `GET /status`: 6-8ms.
- Warm signed retrieve/ack: single-digit ms server-side (curl+openssl process
  forks dominate, as established on 2026-09-23).
- Warm deliver WITH the live guard: 0.8-1.4s per publish. Direct `api.deepseek.com`
  chat completion from this host: 1.4-1.6s. The deliver latency IS the provider
  RTT (the guard calls DeepSeek synchronously before answering). With the key
  absent the same path is ~1s (fail-open after the provider skip). This is
  expected per the docs (blocking classification), not a defect; no PERF row —
  nothing a user would not already know is inherent to the guarded path.
- Fresh-box build (bunker leg): Go toolchain download + `make build` = 31s;
  `make build-mcp` incremental = 1s.
