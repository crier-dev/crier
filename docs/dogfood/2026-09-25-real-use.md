# Dogfood real-use run — 2026-09-25 — relay rate limiter, /docs + /openapi surfaces, registry PATCH liveness

Angle (10th dogfood run; per the angle-change rule the surfaces untouched by
runs 1-9 were taken): the relay **rate limiter** (100 events/min, keyed on
`X-Agent-ID`), the **auth-exempt reference surfaces** (`GET /docs`,
`/openapi.json`, `/openapi.yaml`, `GET /status`), and the **registry PATCH

## Perf (Step 2b)

- 20 signed publishes (curl+openssl fork per publish): 1343 ms total,
  ~67 ms/publish — the cost is process forks, consistent with the 09-23/09-24
  findings (server-side handlers were 20-270 µs). No PERF row: a user waiting
  67 ms on a fork-dominated client loop is not a server defect, and nothing in
  this run made a user wait.
- `GET /docs` 17 ms, `GET /openapi.json` 20 ms warm. Reference surfaces are
  comfortably fast — nothing to profile.

## Trust note (worth a maintainer conversation, not filed as a bug)

The rate limiter keys on `X-Agent-ID`, which any client can claim without
owning the key (publish signatures are presence-only by design). A client can
therefore spend another agent's 100-events/minute budget from its own IP, or
rotate fake ids to sidestep limiting entirely. The registry-keyed identity
that DOES verify (inbox retrieve/PATCH) is the strong path; publish is the
fire-and-forget path. If publish spoofing ever matters in a deployment, the
fix is an authenticated-publish mode or an IP+agent joint key — a design
decision, hence this note rather than a board row.
