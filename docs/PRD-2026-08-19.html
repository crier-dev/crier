1 · Thesis — what we are building

Crier is the messaging primitive for AI agents — the ZeroMQ of agent messaging. One wire protocol, one delivery semantic, any backend: harnesses (Hermes, Claude Code, OpenCode, custom), gateways, scripts, and proxies connect through it and talk to each other as agents, not as clients.

“We are building the zeromq of agent messaging primitive.” — Bane, 2026-08-19

The product promise:

  • Any agent, any backend, one bus. Agents register with an identity, capabilities, and — new in this backlog — an HTTP endpoint schema. Crier handles delivery: durable inbox, live mesh, or push via webhook.
  • Delivery semantics you choose per message: blocking (request/reply, tool-call reply), non-blocking (fire-and-forget), or batched/queued (coalesced webhook POSTs).
  • Context continuity. Messages carry session context; deliveries land in the same context window the conversation lives in — no more orphans.
  • Zero lock-in. The integration surface is an HTTP endpoint schema you supply at install time. “We don't have to build into Hermes — we provide the http endpoint schema template for Hermes http gateway.”
  • Composable networks. One or more relays, linked; agents discover each other across relays and configure themselves on directive (“go have XYZ configure themselves for ABC”).

2 · What exists today (verified)

Wire protocol — WebSocket mesh (docs/mesh-protocol.md)

  • Transport: WS upgrade GET /mesh/connect/{agentID}; NDJSON frames, one JSON object + trailing \n.
  • Envelope: type, version (1), message_id (24-hex), timestamp (RFC3339Nano).
  • Frame types: REGISTER (fire-and-forget), KEEPALIVE (30s), REQUEST (agent→agent RPC, relayed), RESPONSE (routed back via request_id), ERROR (CONTROLLER_OFFLINE, INTERNAL).
  • Sharp edges documented: no crypto on mesh frames (registry is ed25519-signed), no reconnect, silent drops, route table 4096→flush, RESPONSE body is JSON-encoded string.

Registry + durable inboxes (HTTP)

  • Agents: POST /agents (ed25519 key, capabilities), GET /agents, DELETE /agents/{id}.
  • Inboxes: POST /agents/{id}/inbox (deliver), GET .../inbox (retrieve, lease-based), POST .../inbox/ack.
  • Signing contract CR_REQUIRE_AGENT_SIG: X-Agent-ID/Ts/Sig headers, ±30s window, 401/403 — now fully documented in openapi.yaml (CR-GAP-036, shipped tick 229).
  • Memory and PostgreSQL backends; lease TTL default 3600s.

MCP bridge — harness-facing client (cmd/crier-mcp, 13 tools)

  • Registry + inbox tools (8, in-process) + bridge tools (5, new 2026-08-18): send_message, get_messages (auto-ack), ask_agent (blocking inbox RPC), mesh_peers, mesh_request (live WS round-trip).
  • RemoteStore mode: bridge talks to a live server over HTTP (CRIER_HTTP_URL) — N harnesses share one inbox space.

Proven end-to-end (2026-08-18, live)

  • Two-LLM collaboration demo (examples/llm-mesh/): two harnesses, private clues, one puzzle. Bridge lane: 14s, both ACCEPTED. Raw protocol lane: 8s, both ACCEPTED. Report: examples/llm-mesh/REPORT-2026-08-18.html.
  • E2E battery (tick 232): 14/14 probes + 20/20 + 20/20 stress — health, WS subscribe (BUG-001 regression), publish+delivery, mesh connect, signed registry round-trip, SECURITY-001 negatives.
  • Findings that shaped the design: blocking ask deadlocks conversational agents (interruptible polling required); silent frame drops hide client bugs (RFC3339 colon bug); agent→agent REQUEST relay verified live.

5 · Delivery modes

Blocking (request/reply)

Sender issues REQUEST with message_id and expects a correlated RESPONSE. Two paths:

  • Inbox path (exists): ask_agent bridge tool — message + correlation id into target's inbox; reply merged back via crier_reply_to; the harness polls (interruptible — never block exclusively).
  • Webhook path (new): server POSTs the envelope to the target's webhook and waits. A 2xx body is parsed per the endpoint's schema template and returned as the RESPONSE (the “tool call reply”). Timeout / non-2xx → ERROR frame (WEBHOOK_FAILED, with status + retry count).

Non-blocking (fire-and-forget)

Deliver, don't wait. Envelope flag (delivery_mode: "async") or per-agent default. Sender gets a 202 accept; delivery is the server's job (queue + retry).

Batching / queueing

Per-endpoint batch queue: N messages or T seconds (configurable per agent), then ONE webhook POST carrying a batch envelope. Endpoint down → durable queue (persisted, redelivery with backoff, exponential, bounded). Same queue backs blocking-mode retries.

6 · Webhook protocol contract

Envelope (what gets POSTed)

POST {endpoint} HTTP/1.1
Content-Type: application/json
X-Crier-Event: message | reply | configure | batch
X-Crier-Agent: {target_agent_id}
X-Crier-Session: {session_id}          # when present (CR-FEAT-004)
X-Crier-Signature: {hmac/ed25519}      # optional, CR_WEBHOOK_SECRET

{
  "crier": {"version": 1, "message_id": "...", "request_id": "...", "session_id": "...",
            "delivery_mode": "blocking|async|batch", "sender": "agent-a"},
  "payload": { ... }                    # sender-supplied body
}

Response contract

  • 2xx = delivered. Blocking mode: parse body per schema template → becomes the RESPONSE.
  • 4xx = permanent failure (bad schema / auth) → ERROR frame to sender, no retry (except 408/429 → retry).
  • 5xx/timeout = retry with exponential backoff (default: 1s, 2s, 4s, 8s, 16s; CR_WEBHOOK_MAX_RETRIES, default 5) → then ERROR.
  • Endpoint unreachable → durable queue, redeliver on interval / on recovery probe.

Agent registration extension

POST /agents
{ "id": "...", "public_key": "...", "capabilities": {...},
  "webhook": { "url": "https://...", "auth": {"type": "bearer|header", "value_ref": "env:..."},
               "schema_template": "hermes-http-gateway" | "openai-compatible" | "custom",
               "custom_schema": {...},                 # bring-your-own schema
               "delivery_mode": "blocking|async|batch",
               "batch": {"max_messages": 10, "flush_interval_s": 5},
               "retries": 5, "timeout_ms": 30000 } }

7 · Endpoint schema templates — bring-your-own schema

“We don't have to build in Hermes — when we install we provide the http endpoint schema template for Hermes http gateway for different actions. You supply the schema, aka your agent does.”

A template is data, supplied at registration, that maps the Crier envelope ↔ a backend's HTTP API:

  • request_shape — how envelope fields map into the backend's body/headers/query (JSONPath or fixed mapping).
  • action_variants — different actions the endpoint supports (message delivery, tool-call reply, configure, ack).
  • response_map — where the reply text/structured data lives in the backend's response (JSONPath; or “raw body”).
  • auth — how to authenticate to this backend (bearer from env, header from env, none).

8 · Session & context mapping

Requirement: “ability for a script or an agent to map the context window for messages depending on the message so it gets to the same session correctly.”

  • Envelope carries session_id + thread_id + optional source_session_link (how the sender refers to this conversation).
  • The bridge/schema template maps session_id onto the backend's session/thread/context identifier — so follow-up messages land in the same context window.
  • Per-session ordered delivery to webhook targets (FIFO within a session; sessions interleave freely).
  • Round-trip: A→B→A preserves one session id end-to-end; the bridge can attach the originating session to replies so the requester sees the reply in its own conversation.
  • Scripts can remap: a receiver-side script receives session_id, looks up its own mapping, and sets a different session_id on the reply (the “script or agent maps the context window” requirement).

9 · Self-configuration directives

“Go have XYZ configure themselves for ABC.”

  • New message kind configure (X-Crier-Event: configure) with a target capability + schema (optional). Delivered like any message — inbox, mesh, or webhook.
  • Agents advertise capabilities at registration (capabilities), and can update them (new PATCH /agents/{id} or re-register semantics).
  • On receipt, the agent configures itself (register/update webhook, declare capability, load a schema template) and acks the directive.
  • Discovery: GET /agents?capability=abc — “who can do ABC” — then dispatch the directive.
  • Bridge tool: configure_agent (send directive + wait for ack).

10 · Multi-relay federation

“Multiple agents of different backends within my network with one or more relays.”

  • Relay links: CR_FED_LINKS=relay-b=https://relay-b:18767,relay-c=... — a relay connects out to its links (authenticated, e.g. shared secret), not a full mesh.
  • Cross-relay discovery: linked relays exchange agent tables (bounded, cached, TTL) — GET /agents shows remote agents flagged via.
  • Cross-relay delivery: message to a remote agent routes through the link; the remote relay delivers via its own mechanism (inbox/webhook/mesh) and routes the reply back over the same link. Correlation ids must survive hops (the request_id contract is hop-invariant).
  • Failure: link down → durable queue at the source relay; ERROR on TTL expiry.
  • Security: relays are trust boundaries — link auth + optional envelope signing across relays.

13 · Acceptance criteria & KPIs

Product KPIs

  • Time-to-integrate a new backend: ≤ 30 min with a shipped template; ≤ 2 h with a custom schema (target).
  • Delivery reliability: webhook 2xx rate ≥ 99.5% on healthy endpoints (retries excluded); zero message loss on server restart (durable queue).
  • Latency: blocking webhook reply p50 ≤ 2× endpoint latency + 50ms overhead; batch flush latency ≤ flush interval + 100ms.
  • Context continuity: 100% of session-tagged messages delivered with the same session_id end-to-end (round-trip test).
  • Federation: cross-relay delivery p95 ≤ 2× single-relay p95 + 200ms.

Technical gates (every implementation ticket)

  • go build ./... + go vet ./... + go test ./... (8/8 packages) pass; new code ≥ 70% coverage.
  • gitreins guard PASS 4/4 (secrets/build/lint/tests); govulncheck clean.
  • openapi.yaml stays the contract source of truth; spec additions validated (YAML parse + $ref resolution).
  • E2E battery grows: webhook round-trip, blocking reply, batch coalescing, session continuity, federation probes.
  • Every feature has a live-verified demo script under examples/ (evidence-first, per Bane).

Queue growth when endpoints stay downBounded queues (size + TTL per agent), dead-letter with audit event; poison-endpoint circuit breaker
Silent drop behavior hides client bugs (proven 2026-08-18)Webhook driver MUST log parse failures; add server-side log-on-drop for mesh frames (protocol improvement ticket)

Federation trust boundariesLink auth (shared secret v1), per-link allowlists, envelope signing across relays (v2)
Blocking webhook ties server resourcesPer-agent concurrency caps; timeout budget from the sender's REQUEST timeout_ms; no unbounded goroutines

Open questions for the owner

  • Auth model for outbound webhooks: HMAC shared secret (default) vs per-agent ed25519 signing — both?
  • Should the durable webhook queue reuse the Postgres backend or ship a lightweight embedded store (bbolt/SQLite)?
  • Batch envelope shape: flat array of envelopes vs nested batch object — spec decision in CR-SPEC-001.
  • Federation v1: link auth shared-secret sufficient, or OAuth-style token exchange?
  • Does “tool call reply” need the reply to map into the sender's ACTIVE tool call (Hermes-specific) or just a correlated message in the same session (generic)? — CR-FEAT-008 demo decides.
