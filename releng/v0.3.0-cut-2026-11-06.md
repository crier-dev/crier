## UNVERIFIED or RED legs — stated, not hidden

1. **`release.yml` on the tag is RED** (run `42246232196`, `head_sha`
   `e950fdb1e0983ea83d5664fd6549a4ad6297c8a9`, `event: push`, branch `v0.3.0`).
   It failed at `Publish the Release object with every asset` with `asset under
   the same name already exists: [crier_linux_amd64 … SHA256SUMS]`. The cause is
   a duplicate-publish collision: the documented manual path (`make
   release-upload`, step 4 of `docs/releases.md`) published the asset set first,
   and the tag workflow then refused to overwrite it. Both publishers built from
   `e950fdb1`. The workflow — not the tree, not the artifacts — failed, and it was
   not idempotent against an already-present identical set. Fixed under
   `RELEASE-012`; the manual path remains this release's only publisher.

   **Why this cut's run cannot be re-run green** (the `RELEASE-012` acceptance
   allows exactly this arm, and here is the record of it):

   - A GitHub re-run replays the SAME ref and commit (`v0.3.0` /
     `e950fdb1`), so it executes the tag's own tree. That tree's publisher has no
     reconciliation at all — `git show e950fdb1:scripts/release-upload.sh` goes
     straight from the existence probe to `gh release upload … <all 8 assets>`,
     with no comparison — so the collision is deterministic, not flaky.
   - Running the FIXED publisher for `v0.3.0` would not converge either: it
     compares the attached **digests** with the bytes it is about to publish, and
     a fresh build of `e950fdb1` produces different bytes. Measured: rebuilding
     `crier_linux_amd64` at `e950fdb1` with the stamp the published asset itself
     carries (`BUILD_TIME=2026-11-06T15:48:13Z`) reproduces the attached file
     byte for byte — `0e7b2519222b8d264fa201f545d782c0143818a25a8e9e9ae2bd66bc2ec652a1`,
     23,896,226 bytes — so the build IS reproducible and the only difference a
     second build introduces is its own clock stamp. The published set and a
     workflow rebuild therefore differ by construction, and the fixed publisher
     refuses them by design (`CLOBBER` is deliberately never used in CI).
   - Convergence is reachable when a publisher publishes the SAME build twice: a
     half-failed publish re-run with the same `dist/`, or a re-publish after a
     transient failure. It is proven on fixtures by
     `make release-upload-selftest` (arms 5, 5b, 6, 6b, 7, and the neuter arm 8).
   - The tag cannot be moved to a fixed commit (`docs/releases.md`, "What not to
     do"), so no mechanism exists that would turn this specific run green.

   **Remaining gap, named so it is not lost:** a manual `make release` build and
   a CI rebuild of one commit are not byte-identical because `BUILD_TIME` defaults
   to the current clock (`scripts/release-artifacts.sh`). With that stamp derived
   from the commit instead, the manual-then-workflow sequence that produced this
   red would converge on its own. That is a change to the build half, outside
   `RELEASE-012`'s file scope; it is the recommended next row for this class.
2. **Executing the downloaded binary is UNVERIFIED for this pass.** The
   command-approval gate refused the `chmod +x` needed to run a
   `gh release download` payload (downloads arrive mode 0644), and the gate
   block takes the whole command. What IS proven: the published `SHA256SUMS`
   verifies against the downloaded bytes 7/7, and that manifest is byte-identical
   to the one `make release-artifacts` produced and re-verified in the build
   worktree, whose own artifact identity line reads `crier v0.3.0-e950fdb1`.
   The canonical-checkout build of the same commit (different `BUILD_TIME`) also
   printed `crier v0.3.0-e950fdb1` when executed.
3. **The manual upload preceded the tag workflow by ~40 s** and therefore
   preempted it. Stated because the ordering is what produced leg 1.
