`make release-artifacts` and full `ci.yml` on the same commit. INT-CI-019 stays
open and this cut does not claim a bunker-e2e verdict.

## UNVERIFIED or RED legs — stated, not hidden

1. **`release.yml` on the tag is RED** (run `42246232196`). It failed at
   `Publish the Release object with every asset` with `asset under the same
   name already exists: [...]`. The cause is a duplicate-publish collision: the
   documented manual path (`make release-upload`, step 4 of
   `docs/releases.md`) published the asset set first, and the tag workflow then
   refused to overwrite it. Both publishers built from `e950fdb1` and produced
   the same asset set. The workflow — not the tree, not the artifacts — failed,
   and it is not idempotent against an already-present identical set.
   Follow-up filed as RELEASE-012.
2. **Executing the downloaded binary is UNVERIFIED for this pass.** The
   command-approval gate refused the `chmod +x` needed to run a
   `gh release download` payload (downloads arrive mode 0644), and the gate
   block takes the whole command. What IS proven: the published `SHA256SUMS`
   verifies against the downloaded bytes 7/7, and that manifest is byte-identical
   to the one `make release-artifacts` produced and re-verified in the build
   worktree, whose own artifact identity line reads `crier v0.3.0-e950fdb1`.
   The canonical-checkout build of the same commit (different `BUILD_TIME`) also
   printed `crier v0.3.0-e950fdb1` when executed.
3. **The manual upload preceded the tag workflow by ~40 s** and therefore
   preempted it. Stated because the ordering is what produced leg 1.
