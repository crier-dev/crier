Authority view · read-only

Principals, bindings, grants and agent class — the ACL this server serves. Collapse this fold and nothing is read.

Fetched once on page load (the fold opens by default), when the fold is reopened, and on request. While the fold is closed no management read is issued, and a refused read is reported once, not retried. Records are deployment-wide, not filtered to the selected conversation. No credential entry, minting or permission changes here.

Permissions reads require CR_PERMISSIONS_ENABLED=true and a distinct CR_PERMISSIONS_ADMIN_TOKEN. Trust records require that distinct token even with delivery ACLs off. An authorized deployment gateway must supply access; this page does not collect or store tokens.

Principals

Loading GET /principals…

ID identifies the credential holder; kind is the record type; display_name is the human label; namespace is the recorded realm; role and status are stored authority/lifecycle values; created_at is creation time. An omitted field is not reported, not an inferred default. A token fingerprint is shown only as a short prefix, labelled as such in the column header; a token or a full hash is refused in words, never rendered.

Bindings

Loading GET /bindings…

id is the binding record; kind is its type; principal is the credential holder; agent is the bound agent; as_agent permits acting as that agent; created_at is creation time; created_by names the author. The endpoint returns the effective record per principal/agent pair.

Grants

Loading GET /grants…

id identifies the grant; kind is its type; principal is the grantee; subject.type/ref identify the target; actions are permitted operations; granted_by/at record who and when; expires_at is the expiry (null means no expiry); revoked_at/by record revocation; note is the author's explanation. Only current, unexpired, unrevoked grants are returned.

Agent class & scope

Reading an agent class requests GET /agents/{id}/class, which the management surface serves behind its admin credential: the request must present the deployment's CR_PERMISSIONS_ADMIN_TOKEN as its Bearer credential. This page never sends an Authorization header and collects no tokens, so it cannot present that credential itself — the control below is offered only where the server's own posture readback proves this viewer's requests already clear that gate, and an authorized deployment gateway or an authorized operator client holds the credential otherwise.
