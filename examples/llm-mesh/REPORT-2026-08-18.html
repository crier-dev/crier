The question

Can Crier actually carry a collaboration between two LLMs — and can they solve a problem together?

Yes — and the exercise exposed what was missing. Crier already had the messaging: the WebSocket mesh (REQUEST/RESPONSE frames, correlation ids) and durable per-agent inboxes. What it did not have was the layer between an LLM harness and the wire. As Bane put it:

“Right now the messaging exists but it requires the harnesses to read the data directly.”

The fix: a bridge — crier-mcp — that owns the transport (sockets, leases, acks, correlation ids) and exposes it to harnesses as plain MCP tools. Harnesses never see the wire.

What was built

Go — inside the crier repo

  • RemoteStore (internal/registry/remote.go): a store implementation that talks to a running Crier server over its HTTP API — so any number of bridge processes share one server's agents and inboxes.
  • 5 new MCP tools (internal/mcp/): send_message, get_messages, ask_agent (blocking request/reply over the durable inbox), mesh_peers, mesh_request (live WebSocket round-trip). The bridge owns every transport detail.
  • Mesh bridge (internal/mcp/meshbridge.go): one WebSocket connection per bridge process, REGISTER handshake, frame correlation, auto-answer for incoming REQUESTs (liveness lane), startup reconnect retries.
  • Env config: CRIER_HTTP_URL, CRIER_AGENT_ID, CRIER_MESH_URL.

Python — examples/llm-mesh/

  • harness.py — an LLM agent whose only interface to Crier is MCP tools: get_messages, ask_peer, answer_peer, submit_final. No WebSockets, no HTTP to the registry, no signing, no leases.
  • controller.py — a third harness-side peer: collects finals, verifies against ground truth, sends verdicts, and exercises the live mesh lane (peers + PING).
  • mcp_client.py — minimal MCP stdio client (the generic harness↔bridge interface).
  • mesh/ — the raw-protocol lane: same puzzle, agents speaking the mesh wire directly (crier_mesh.py client), for comparison.

Architecture

Harnesses talk only to their bridge, over MCP. The bridge talks to the server over its HTTP inbox API and holds one WebSocket to the mesh. LLM content rides the durable inbox; the mesh is the live lane (peers, pings, liveness).

Finding 2 — the silent-drop timestamp bug

The raw lane failed silently at first. Every frame the Python client sent was dropped by the server — no error, no log. Cause: the client's timestamps were -0500 (missing the colon), which is not RFC3339; Go's time.Time JSON unmarshal rejects the frame, and the protocol's documented behavior is to silently drop malformed frames.

Fixed by emitting proper RFC3339 (-05:00) timestamps. The lesson: the protocol's silent-drop design makes client bugs invisible — validation belongs in the client, or the server should at least log parse failures. (This is a candidate protocol improvement: log-and-drop instead of drop.)

The deadlock finding

Found in the first bridge-lane run: both agents called the bridge's blocking ask_agent as their first action. Each waited 60s for a reply the other never sent — because the other was also blocked and never checked its inbox. Two-way synchronous RPC deadlocks a conversational system.

Fix: the harness now uses interruptible polling — send the question (with its own correlation id), then poll get_messages while waiting, answering any incoming questions on the spot with a fact-bound responder call. The second run completed cleanly in ~14s with zero deadlock.

Design rule this teaches: blocking request/reply is fine for one-shot RPC; conversational agents need interruptible waits. The raw lane's architecture (responder on the connection thread, solver on its own) avoids the problem structurally. The bridge's ask_agent remains useful for non-conversational callers.

Protocol notes the exercise surfaced

  • No automatic reconnect — a dropped mesh socket is closed for good; the bridge retries only at startup.
  • Incoming mesh REQUESTs to a bridge are auto-answered bridge_alive — the mesh is the liveness lane, the durable inbox is the content lane for LLM traffic.
  • RESPONSE body is a JSON-encoded string on the wire (RawMessage quirk) — the bridge hides this.
  • Mesh identity is a claim — no cryptographic auth on mesh frames; registry-side signing (CR_REQUIRE_AGENT_SIG) is enforced by the server, but bridge-side signing on the harness's behalf is not yet implemented (demo runs with signing disabled).
  • Blocking ask deadlocks two agents that both ask first — see finding above.

How to run it

cd examples/llm-mesh
./run-demo.sh            # bridge lane (harnesses use MCP tools only)
./mesh/run-demo.sh       # raw protocol lane (agents speak the wire directly)

Requires DEEPSEEK_API_KEY (model: deepseek-v4-flash). Each run starts its own Crier server, prints the full conversation, exits 0 only if both agents solved the puzzle.
